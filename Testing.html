Testing guide

Running tests

You can run tests in two ways.

  • Method 1: Using IntelliJ JUnit test runner
    • To run all tests, right-click on the src/test/java folder and choose Run 'All Tests'
    • To run a subset of tests, you can right-click on a test package, test class, or a test and choose Run 'ABC'
  • Method 2: Using Gradle
    • Open a console and run the command gradlew clean test (Mac/Linux: ./gradlew clean test)

Link: Read this Gradle Tutorial from the se-edu/guides to learn more about using Gradle.

Types of tests

Command cleanup regressions retain the existing owner suites. ArgumentTokenizerTest additionally checks the legacy edit grammar's ASCII-space boundaries, embedded slashes, unknown prefixes and empty values. StudentFieldIntegrationTest checks clearing a selected filtered record, saving/reloading an empty register, repeated clearing, and atomic failure preservation. AddStudentUiTest verifies failed clearing retains the selected row/details and successful clearing resets both through the real command box.

This project has three types of tests:

  1. Unit tests target the lowest-level methods and classes.
    For example: tutorconnect.commons.util.StringUtilTest
  2. Integration tests check how multiple code units work together; the individual units are assumed to work.
    For example: tutorconnect.storage.StorageManagerTest
  3. Hybrid tests combine unit and integration testing. These tests check both the individual units and how they work together.
    For example: tutorconnect.logic.LogicManagerTest

F01–F08 acceptance

Student discovery (F03, stories 10 and 15) adds focused FindCommandParserTest, NameContainsKeywordsPredicateTest, FilterCommandParserTest, FilterCommandTest and StudentCriteriaPredicateTest coverage. Run StudentDiscoveryIntegrationTest for real command parsing, full-register query replacement, all seven indexed mutation targets and persisted UUIDs, no-save queries, error preservation, and schedule independence. StudentDiscoveryUiTest runs with F01_UI_TESTS=true and verifies rendered result numbering, empty placeholders and selection through the command box.

Manual discovery check: add three students, give rows 2 and 3 the same level, then filter l/LEVEL. The matching rows should be numbered 1 and 2 in stored order. Change the first displayed student's level to a different level: only that student changes, disappears from the current filter, and selection clears. Use a partial-name find to retrieve that student from the full register, then list to restore all rows. Check the weekly schedule remains independent throughout.

Coordination is tracked in acceptance issue #79. Each owner remains responsible for their feature's tests and fixes. The final integrated acceptance snapshot is f08-04-ui-schedule at 93ad5cf0, combining master 7b6cc481, scheduling integration 9f7146e6 and persistence integration 324be3a6. The review PRs are retargeted to master in order; temporary dependency branches are review bases and must not be merged as product branches.

Use JDK 25 as configured in build.gradle. On a desktop or configured virtual display, run:

env F01_UI_TESTS=true F06_UI_TESTS=true F08_UI_TESTS=true ./gradlew check shadowJar coverage --offline --no-daemon
sh .github/run-checks.sh
git diff --check

Omit --offline if dependencies are not cached. Without the environment flags, desktop UI tests are skipped; that run alone does not certify details/selection/summary behavior.

The F08 automated acceptance includes:

  • WeeklySlotTest: all seven days and exact aliases in all cases, Unicode normalization, strict valid time boundaries, invalid formats/ranges/controls, required components and minute precision.
  • ScheduleCommandParserTest/ScheduleCommandTest: both prefix orders, structural/value precedence, missing/repeated/unknown parameters, invalid/oversized/displayed indexes, set/replace/no-change and overlaps.
  • WeeklySlotFieldTest/WeeklySlotPersistenceTest: complete canonical pairs, missing/null legacy slots, invalid partial records, all-weekday reloads, stable identity and unrelated optional data.
  • WeeklySchedulingIntegrationTest: save-before-publish, byte/object/filter/selection preservation on partial-write and atomic-move failures, both unset or both old components, no-save normalized input, filtered overlaps and removal of attached slots by delete.
  • WeeklyScheduleTest/WeeklyScheduleUiTest: independent weekday/time ordering, insertion-order ties, immediate replacement/deletion refresh, em-dash/full-name formatting, actual command-box status/selection, unchanged details/summary on errors or no-change, and persisted deletion. The real window test also runs guardian, level, subject and rate updates on a scheduled student, checks all details, reloads through list, and verifies slot replacement preserves every unrelated optional field.

For an additional manual smoke run in a fresh data directory, add Zoe and Amy using add n/Zoe p/81234567 a/21 Clementi Ave and add n/Amy p/81234567 a/22 Clementi Ave. Schedule Zoe on Sunday 23:59 and Amy on Monday 09:00. The register stays Zoe/Amy while the summary is Amy/Zoe. Reschedule both to Tuesday 19:00; the tie becomes Zoe/Amy. Repeat Zoe's slot with d/tUE; selection stays on Amy and there is no save. Try invalid values, restart, and delete each student to check persistence and removal.

Reproducible release demonstration

Use a new disposable demo directory, separate from normal application data. Copy the packaged JAR there, create data/addressbook.json containing {"persons":[]}, and run java -jar tutorconnect.jar from that new directory. This avoids the sample records and makes the following visible indices reproducible. The refactored artifact is tutorconnect.jar; the legacy data/addressbook.json location and persons JSON key remain unchanged.

  1. Add add n/Zoe p/81234567 a/21 Clementi Ave, then add n/Amy p/82345678 a/22 Clementi Ave.
  2. Run schedule 1 d/Sun t/23:59, then schedule 2 t/09:00 d/Mon. The register remains Zoe/Amy; the summary is Amy Monday 09:00, Zoe Sunday 23:59. Amy is selected and her details show the complete slot.
  3. Run find Amy, then schedule 1 d/Mon t/00:00. Visible index 1 resolves to Amy. The register contains Amy, while the summary still includes Zoe. Restore Amy with schedule 1 d/Mon t/09:00, then run list.
  4. Run guardian 1 g/91234567, level 1 l/Sec4, subject 1 s/Math/Science, and rate 1 r/75. Schedule Zoe with schedule 1 d/Tue t/19:00, then Amy with schedule 2 d/Tue t/19:00. Overlaps are accepted; the summary tie follows Zoe/Amy insertion order. Select Zoe to inspect that her unrelated fields remain intact; select Amy again for the next step.
  5. Run schedule 1 d/tUE t/19:00. Expect a no-change result and selection to remain on Amy. Run schedule 1 d/Mon t/24:00 and schedule 1 d/Mon; expect errors with existing slots unchanged.
  6. Close and reopen from the same demo directory, then run list and inspect both schedules and Zoe's fields.
  7. Run delete 1; Amy becomes index 1 and the summary contains only Amy. Run delete 1 again; the summary says No weekly lessons scheduled. and details prompt for selection.

The screenshot fixture intentionally shares the students' phone number; the manual sequence uses distinct numbers to avoid the unrelated shared-phone warning. Indices always refer to the visible student register, never the separately sorted summary. Do not perform the deletion demonstration against real student data.

Draft scheduling release notes

  • Schedule one recurring weekly lesson per student using schedule INDEX d/DAY t/TIME.
  • Accept full English weekday names or three-letter aliases, case-insensitively, with strict 24-hour HH:mm times.
  • Replace a complete slot in one command; equivalent normalized input reports no change.
  • View lessons ordered by weekday and time, with register insertion order breaking ties, independently of filtering.
  • Preserve student details and persist weekly slots across reloads; deletion also removes the student's slot.
  • Allow students to share a day/time. This feature does not provide lesson durations or conflict detection.
